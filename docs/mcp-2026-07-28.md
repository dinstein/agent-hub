# MCP 2026-07-28

What the 2026-07-28 specification changed, what AgentHub does about it on each face, and what is
deliberately still absent.

**The section numbers here are an interface.** `internal/mcp`, `internal/mrtr`, `internal/gateway`
and `test/mcpstub` cite them from doc comments, and [canonical.md](canonical.md) §5b points at §6.1
and §7. Renumbering silently redirects every one of those.

Upstream specification: <https://modelcontextprotocol.io/specification/2026-07-28>  
Changelog from 2025-11-25: <https://modelcontextprotocol.io/specification/2026-07-28/changelog>

---

## 1. What the specification changed

### 1.1 Breaking changes

**Stateless protocol — no `initialize` handshake.** The `initialize` /
`notifications/initialized` round-trip is gone; what it established now travels on every request,
in `_meta`:

| Key | Required | Value |
|-----|----------|-------|
| `io.modelcontextprotocol/protocolVersion` | Yes | `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | Yes | `ClientCapabilities` object |
| `io.modelcontextprotocol/clientInfo` | SHOULD | `Implementation` object |

Servers SHOULD echo `io.modelcontextprotocol/serverInfo` in every result's `_meta`. A request
missing a required field is rejected with `-32602`, and HTTP 400 on HTTP transports.

**`server/discover` — a new RPC servers MUST implement.** It returns the supported protocol
versions, capabilities and server identity, so a client can pick the highest mutually supported
version before sending anything else. Its absence is also the backward-compatibility probe: a
server that does not answer it is a pre-2026 server, and the caller falls back to `initialize`.

**`resultType` on every result** — `"complete"`, or `"input_required"` (below). An absent
`resultType` means `"complete"`, which is what makes a 2025-11-25 result readable.

**Multi Round-Trip Requests (MRTR) replace server-initiated RPCs.** Servers can no longer call
`roots/list`, `sampling/createMessage` or `elicitation/create` back at the client. A server needing
input answers `tools/call`, `prompts/get` or `resources/read` with:

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": { "key1": { "method": "elicitation/create", "params": {} } },
    "requestState": "<opaque AEAD-protected blob>"
  }
}
```

The client collects the inputs and retries the **original** request under a **new** JSON-RPC id,
carrying `inputResponses` and the echoed `requestState`. Clients MUST NOT inspect or modify
`requestState`; servers MUST treat it as attacker-controlled input.

**Streamable HTTP loses sessions and resumability.** `Mcp-Session-Id` is gone — no capture, no
DELETE on close. `Last-Event-ID` and SSE event ids are gone, so a broken response stream is a lost
request that must be re-issued under a new id. The GET notification stream is replaced by
`subscriptions/listen`: one long-lived POST-response SSE stream that also absorbs
`resources/subscribe` / `resources/unsubscribe`. Clients opt into `toolsListChanged`,
`promptsListChanged`, `resourcesListChanged` and `resourceSubscriptions`, and each event carries
`io.modelcontextprotocol/subscriptionId` in `_meta` for correlation.

**Every POST must carry `Mcp-Method`** (the JSON-RPC method name) **and `Mcp-Name`** (the tool /
resource / prompt name, when one applies).

| Removed | Replacement |
|---------|-------------|
| `ping` | (none; omit) |
| `logging/setLevel` | `io.modelcontextprotocol/logLevel` in request `_meta` |
| `notifications/roots/list_changed` | (deprecated — use MRTR) |
| `resources/subscribe`, `resources/unsubscribe` | `subscriptions/listen` |
| HTTP GET notification stream | `subscriptions/listen` |

Error codes were renumbered into the range the specification now reserves for itself,
`-32020`–`-32099`. `-32000`–`-32019` is legacy: grandfathered for codes already out there, but
**nothing new may be allocated in it**, and an implementation's own codes belong outside the whole
`-32768`–`-32000` reserve. AgentHub's two (`mcp.CodeBusy`, `mcp.CodeRateLimited`) are positive for
that reason; `mcp.IsAppErrorCode` is the check.

| Code | Name | Old code | Required `data` |
|------|------|----------|-----------------|
| `-32020` | `HeaderMismatch` | `-32001` | (none) |
| `-32021` | `MissingRequiredClientCapability` | `-32003` | `{requiredCapabilities}` |
| `-32022` | `UnsupportedProtocolVersion` | `-32004` | `{supported, requested}` |
| `-32602` | resource not found (JSON-RPC Invalid Params) | `-32002` | (none) |

The two payloads are not decoration: the backward-compatibility flow tells a client meeting `-32022`
to retry with a version from `supported`, which it cannot do when the list never arrives.

### 1.2 Minor additions

- **`CacheableResult`**: the list results and `resources/read` carry `ttlMs` (a freshness hint) and
  `cacheScope` (`"public"` or `"private"`).
- **`extensions`** in `ClientCapabilities` / `ServerCapabilities`, for opt-in behaviour beyond the
  core protocol.
- **Tasks** promoted from experimental to the official `io.modelcontextprotocol/tasks` extension,
  redesigned around polling (`tasks/get`) and client-to-server input (`tasks/update`).
- **Deterministic `tools/list` ordering**, recommended for LLM prompt cache hit rates.
- **OpenTelemetry** `traceparent` / `tracestate` / `baggage` in `_meta`, per W3C Trace Context
  (reserved key names; propagating them is available, not required — §7.13).
- **OAuth**: `iss` validation (RFC 9207) before redeeming a code, `application_type` required in
  DCR requests, and Client ID Metadata Documents as the preferred DCR replacement.

### 1.3 Deprecations

A window of at least twelve months applies to all of these; the earliest removal is 2027-07-28.

| Feature | Migration |
|---------|-----------|
| `roots` | Pass directories via tool params, resource URIs, or server config |
| `sampling` | Integrate directly with LLM provider APIs |
| `logging` | Write to `stderr` (stdio) or use OpenTelemetry |
| HTTP+SSE transport | Migrate to Streamable HTTP |
| OAuth DCR (RFC 7591) | Use Client ID Metadata Documents |

Each use site in this tree carries a `// DEPRECATED-UPSTREAM(<feature>, earliest-removal: <date>)`
comment, so one grep finds them all; [canonical.md](canonical.md) §5b tracks the seams.

## 2. The client face: what AgentHub sends downstream

Landed in three phases — the transport, then MRTR (phase 2), then subscriptions and OAuth
(phase 3).

**Handshake.** `transport.Handshake` tries `server/discover` first, and `mcp.NegotiateHighest`
picks the newest entry in `mcp.SupportedVersions` the server also advertises from the result's
`supportedVersions`. The server's identity arrives in the result's `_meta` under
`io.modelcontextprotocol/serverInfo`, not as a top-level member, and `instructions` is carried on
this path as well as the legacy one. When discover fails in a way that proves the server answered —
`discoverFallback`, §7.6 — the legacy `initialize` path runs instead and sends
`notifications/initialized` as before. **An error code the specification reserves for itself
(-32020 to -32099) is not such a proof**: only a modern server can produce one, so it propagates
rather than triggering a fallback that would send `initialize` to a server that does not implement
it. The negotiated version is recorded on the transport, and nothing above `internal/downstream`
needs to know which generation is in use.

**Per-request `_meta`.** On a 2026 connection every outgoing request carries what
`transport.BuildRequestMeta` produced, spliced into the params by `injectMeta`, and streamable-HTTP
POSTs additionally carry `Mcp-Method` / `Mcp-Name`. `MCP-Protocol-Version` is read back out of the
body being sent (`versionForHeader`) rather than from transport state, because the two MUST agree
and `server/discover` is precisely the request where they otherwise would not: it declares
2026-07-28 before anything is negotiated. `Mcp-Name` comes from `params.name` or `params.uri` and is
base64-sentinel-encoded when it is not header-safe. `server/discover` is itself a 2026-shaped
request, so it carries all of this before negotiation has happened. The client capabilities declared
there are empty (§7.2).

**MRTR.** `Server.Call` in `internal/downstream` re-issues a request that came back
`input_required` under a new id, echoing `requestState` verbatim and carrying the inputs
`mrtr.Resolve` collected through the `mrtr.Handler` seam — filled with the same peer-handler
adapter that answers legacy reverse RPCs, so both protocol generations answer identically. Four
rounds maximum, each re-entering the breaker gate and the owner queue. `requestState` never enters
`internal/mrtr` at all: the package boundary is what enforces "the coordinator cannot inspect or
modify it".

`inputRequests` is optional, and a result carrying only `requestState` is the **load-shedding**
shape the specification names: the server asks for nothing and the client retries immediately with
the token echoed. That round skips `mrtr.Resolve` entirely — there is nothing to resolve — and
`maxInputRounds` is what stops a server that only ever sheds. A result carrying **neither** member
still fails closed on the first round: the retry would be byte-identical, and it is the one
`InputRequiredResult` a server must not send. `requestState` is a pointer for the same reason
`Cursor` is: "echo the exact value" and "send none at all" are different instructions, and a plain
string cannot tell absent from empty.

**Subscriptions.** On the 2026 path `subscriptions/listen` replaces the GET notification stream. Its
`params.notifications` is a `SubscriptionFilter` — an allow list of booleans plus a
`resourceSubscriptions` URI list — opting into the three list-changed types and nothing else;
`resourceSubscriptions` stays nil rather than empty, since subscribing to no resource is not the
same as subscribing to an empty set. Events dispatch by notification method name. The
acknowledgment the server MUST send first is read and its declines logged: a type the server
omitted will never arrive, and without that line "this server never announces tool changes" and
"this server's tools have not changed" are the same observation. Both streams are gated by the same
`HTTPConfig.NotificationStream` and opened at most once per transport.

**OAuth.** RFC 9207 `iss` validation runs before the authorization code is redeemed and fails
closed; DCR requests carry `application_type`. Client ID Metadata Documents are a seam only —
`NewClientIDMetadataRegistrar` returns `ErrNotImplemented`, because publishing a metadata document
needs a stable https URL and a local process has no hosting story for one. DCR stays the
registration path through the deprecation window, and migrating is a constructor swap.

Session and resume handling in `internal/mcp/transport/streamablehttp.go` is deliberately **kept**,
not removed: §3's fallback path still speaks `Mcp-Session-Id` / `Last-Event-ID`. A 2026 connection
simply never receives a session id. Removal waits for the deprecation window to close.

## 3. Version negotiation and backward compatibility

| Scenario | Behaviour |
|----------|-----------|
| Downstream speaks 2026-07-28 | `Handshake` → `Discover`, stateless `_meta` path, no `initialize` |
| Downstream speaks 2025-11-25 or older | `Handshake` → answered failure → legacy `initialize`, session and resume path |
| Upstream client speaks 2025-11-25 or older | `initialize` negotiates the stateful family only, and the session never sees a 2026 member — `replyResult` strips them |
| Upstream client speaks 2026-07-28 | `server/discover` answers with every supported version; a request carrying `_meta` runs stateless, receives `resultType` on every result, and is never sent a reverse RPC. `-32022` for a version the gateway cannot serve statelessly |

The negotiated version on each transport gates every version-specific path, which is why the
generations never have to be reasoned about above `internal/downstream`.

## 4. Test servers

No production MCP server speaks 2026-07-28 yet, so conformance rests on one stub. The two SDK betas
below were planned and never built (§7.7).

### 4.1 In-process Go stub — `test/mcpstub`

The stateless surface a conformant client exercises: `server/discover`, `tools/list` with
`resultType` and freshness hints, `tools/call`, and one MRTR round through its `confirm` tool. It
is **strict on purpose** — missing `_meta`, a wrong declared version, an `MCP-Protocol-Version`
header disagreeing with the body's `_meta`, an `Mcp-Method` / `Mcp-Name` header disagreeing with the
body, or a `requestState` not echoed verbatim is rejected with the spec's own error code — so a
passing client test is wire-level evidence rather than a smoke test. It also refuses a `_meta` with
no `clientCapabilities`, an MRTR retry that reuses the original JSON-RPC id, and a retry whose
arguments changed — the last two being rules only this stub can observe, since the fake transport
the unit tests use takes params without an id at all. It decodes a base64-sentinel `Mcp-Name` before
comparing, and its `-32022` carries the `supported`/`requested` payload, because a stub that skipped
either would let a client that got them wrong pass.

Its `shed` tool covers the other MRTR shape — `requestState` with no `inputRequests` — so the
load-shedding round has wire-level proof and not only a fake-transport unit test. The retry there
owes one rule the `confirm` retry does not: a round that asked for nothing must come back with no
`inputResponses`.

**What it still does not check**, so that the evidence is not read as broader than it is: that
`inputRequests` / `requestState` are never applied to a request sent in parallel.

`clientInfo` was on that list and should not have been. It is optional, and the specification says
clients SHOULD send it "unless specifically configured not to do so" — so a stub refusing its
absence would grade a conformant client as broken, which is the mistake a deliberately strict stub
is most likely to make. Absence passes; a PRESENT one missing `name` or `version` is refused,
because `Implementation` requires both. Strictness that outruns the specification is not
strictness.

The parallel rule is worth one sentence on why it stays unchecked rather than being hard: a
downstream's calls are serialized by the owner queue (`internal/downstream`, one owner goroutine per
server), and `requestState` lives on the local params of each `CallFor`, so two calls cannot share
one. A test would prove a property that holds twice over by construction — which is a reason to
record the reasoning here, not to write the test. The version-header check is
the one a client can only fail before it has negotiated anything, and its absence is why that defect
survived to be found by reading the specification rather than by running the suite.
It has no external dependencies and runs under `go test ./...`. It deliberately does not offer
`subscriptions/listen`; those mechanics are pinned at the transport level instead.

### 4.2 Go SDK beta — not built

The plan was `github.com/modelcontextprotocol/go-sdk` pre-release under `//go:build integration`,
kept out of `make ci` because it needs the network. Nothing is wired: no such build tag exists in
the tree, and neither does the target that was to run it.

### 4.3 Python SDK beta — not built

The plan was a `mcp` Python SDK beta server run as a subprocess for cross-language validation,
behind `TEST_PYSERVER=1`. `test/pyserver/stub_server.py` is a placeholder comment and nothing more.

## 5. The server face: what AgentHub exposes upstream

Both generations are served, and which one a session gets is decided by what its first requests
look like:

- **`server/discover`** answers immediately with every supported version, in `supportedVersions`,
  with the gateway's identity in the result's `_meta` and the `ttlMs` / `cacheScope` a
  `CacheableResult` requires. A request carrying the per-request `_meta` flips the session into
  stateless mode — capabilities recorded, session counted as initialized, `-32022` (carrying its
  `supported` / `requested` payload) for a version the gateway cannot serve statelessly.
  `initialize` negotiates the **stateful family only**, so a client declaring 2026 there is
  answered with the default rather than having its claim echoed back at it.
- **`replyResult` is the single normalization point.** A stateless session always sees
  `resultType`; a stateful one never sees the member a 2026 downstream happened to include; and
  `content` is always an array, because it is required to be one and a downstream that omitted it
  (or sent null) would otherwise put an invalid result out under agenthub's name. On the 2026 face
  `tools/list` also carries `ttlMs` (60s) and `cacheScope: private`.
- **A stateless session is never sent a reverse RPC**, whatever its `_meta` declared.
- **`internal/httpbridge`** accepts the stateless shapes without a session and mints none for them
  — the per-caller state behind the dispatcher is keyed by authenticated identity, not by a header.
  `Mcp-Method` / `Mcp-Name` / `MCP-Protocol-Version` are validated against the body (`-32020`,
  HTTP 400), and a request carrying `_meta` must carry `Mcp-Method`. `Mcp-Name` is decoded from the
  base64 sentinel before the comparison and sourced from `params.uri` as well as `params.name`; a
  sentinel-shaped value that does not decode is refused rather than compared as a literal. The
  version header answers to **two** rules, and conflating them is how the second one stayed missing:
  a value naming a version outside `mcp.SupportedVersions` is refused (`-32022` carrying the
  supported list, HTTP 400) on every verb including `DELETE`, which every revision defining the
  header requires as a MUST; a value *disagreeing with the `_meta` of the same body* is `-32020`.
  Only **absence** is allowed, and only because the header postdates 2025-03-26 and the
  specification tells a server to read its absence as that version. The `_meta` comparison alone
  could not cover the first rule: a ≤ 2025-11-25 request carries no `_meta`, so there was nothing
  to compare against for exactly the generations whose specification demands the refusal.
- **The HTTP status follows the error code** where the binding assigns one: `-32020` / `-32021` /
  `-32022` are 400, and `-32601` is 404 **on a 2026 request only**. That gate is load-bearing: a
  ≤ 2025-11-25 client never agreed to the 404 rule, and agenthub's own downstream client reads a 404
  as a dropped session, so answering a legacy caller's unknown method with one would turn "no such
  method" into a reconnect loop. Everything the specification assigns no status to stays 200.

The gateway serves tools only — `initialize`, `server/discover`, `ping`, `tools/list`,
`tools/call`, shutdown. Everything else is method-not-found, including `subscriptions/listen`
(§7.1) and every resource and prompt method (§7.3).

## 6. Decisions

1. **`mcp.ProtocolVersion` never flips to `"2026-07-28"`.** The original plan was to flip it once
   the transport work was conformant. It stays at `Version2025` instead, because every reader of it
   is definitionally pre-2026: the legacy initialize declaration (which only runs after
   `server/discover` failed), the exposure side's `initialize` answer, the HTTP header sent before
   negotiation, and fakemcp's scripted default. The 2026-07-28 declaration travels per-request in
   `_meta`, built by `transport.BuildRequestMeta` from `Version2026` directly, so flipping the
   constant would only corrupt the places where 2025-11-25 is the correct answer. The constant's
   doc comment in `internal/mcp/version.go` carries the same warning.

2. **`sampling/createMessage` is refused**, and `sampling` is not declared in the capabilities sent
   downstream. AgentHub does not route LLM calls, and declaring a capability it cannot serve would
   turn an up-front refusal into a mid-call failure.

   This entry used to claim the refusal carries `-32021` `MissingRequiredClientCapability`. It does
   not, and it should not. `-32021` is a **server** telling a **client** which capability it failed
   to declare, and on this seam the roles are the other way round: the downstream is the server,
   AgentHub is the client, and the capability that is missing is AgentHub's own.
   `mrtr.ErrSamplingUnsupported` aborts the MRTR round and the `tools/call` surfaces upstream as an
   internal error. The code has no legitimate emit site in this tree — the gateway would need one
   only if it forwarded an `input_required` upward, which §7.4 says it does not — so
   `mcp.CodeMissingRequiredClientCapability` stays defined and unused rather than being spent on a
   case it does not describe.

3. **The `tasks` extension is not implemented.** The `fetch_result` meta-tool already covers the
   paginated-result case that motivates it. Revisit once the extension stabilizes post-GA.

## 7. Deliberately absent

Each entry names the gap, the current (fail-closed) behaviour, and where the seam is.

### 7.1 No out-of-band notification stream on the HTTP face

`subscriptions/listen` lands in the gateway's dispatch default, so a conforming 2026 client reads
it as "this server offers no stream" — the same stance canonical.md §5b froze for the legacy GET
stream it replaces. The stdio face pushes notifications inline, as it always has.

### 7.2 Extensions are not forwarded

The capabilities AgentHub declares downstream (`clientCapabilities2026`,
`internal/mcp/transport/initialize.go`) are empty: no extensions, no sampling, nothing. A
conforming server therefore never activates an extension and serves the non-extension fallback its
spec obliges it to carry. The upstream client's own declaration is deliberately not relayed — the
server's counterparty is AgentHub, and AgentHub must declare only what it can itself deliver.

Passthrough later means an allowlist decided one extension at a time. A blanket forward is wrong in
exactly the way a blanket capability declaration is wrong: the server would send payloads nothing
here can honour.

### 7.3 Resources are not proxied, so `ui://` cannot flow

MCPApp/UI content is delivered as `ui://` resources, which no client can fetch through AgentHub.
UI support is three stacked pieces in order: resource proxying on the exposure side, through the
same governance pipeline as tool calls; the §7.2 allowlist; and only then UI passthrough for
clients that opted in. Until then every client gets the server's text fallback.

### 7.4 MRTR answers only what the legacy path answered

`elicitation/create` fails with method-not-found — the same answer the legacy reverse-RPC path
gives, so the two generations stay in parity. Answering it needs a channel to a human that this
product deliberately does not have; the seam is `mrtr.Handler`, and `resolveInputs` in
`internal/downstream/server.go` is where a richer handler installs.

Now that the exposure side speaks 2026 (§5), a second path exists for sessions whose **upstream**
client is also 2026-07-28: forward the downstream's elicitation upward as the gateway's own
`input_required`, and let the client collect the input from its human. The cost is a double echo
done right — the gateway holds the downstream's `requestState` while minting its own for the
upstream leg, and neither side may ever see the other's. Worth building only once a real 2026
client exists to drive it.

### 7.5 Freshness hints upward are the gateway's constant, not the downstream's

The result surface is settled in one place: `replyResult` stamps `resultType` for a stateless
session and strips it for a stateful one, and `tools/list` carries `ttlMs` and `cacheScope` on the
2026 face (§5). What is still a constant is the hint itself — 60s and `private`, decided by the
gateway. Propagating a downstream's own freshness hints upward is meaningful only once per-server
list results are surfaced individually, which is not how the aggregated catalog answers today.

### 7.6 Handshake probe hardening — evaluated, deferred with evidence

**Probing at all is a choice between two revisions, and the newer one wins.** 2025-11-25 says "the
initialization phase MUST be the first interaction between client and server", so sending
`server/discover` ahead of `initialize` is, by that revision's letter, out of order. 2026-07-28
resolves it deliberately: probing is RECOMMENDED on stdio, the three fallback outcomes are defined,
and the reason given is that some legacy servers do not validate that a request arrives after
`initialize` and would process an era-ambiguous method under legacy semantics. A client that speaks
the newer revision follows the newer revision; the empirical pass below is what says real servers
agree. This paragraph exists because the tension is easy to rediscover and read as a defect.

`discoverFallback` falls back to `initialize` only on proof the server answered **and is old**: a
JSON-RPC error outside the range the specification reserves for itself, or a `ClassFatal` HTTP 4xx
whose body carries no such code either. A server that crashes, hangs, or answers 5xx to an unknown
method therefore fails to connect where it happened to work before. Two hardenings were designed
and deferred after an empirical pass — a real stdio TS SDK server and two production
streamable-HTTP servers all fell back cleanly: widening the fallback to any answered HTTP response,
and a per-server `protocol: legacy` registry field that skips the probe. Reach for the escape hatch
first if a real server trips this; it is also the operator's immediate mitigation.

**The stdio binding names the hanging case, and the deferral was re-read against it.** Its
backward-compatibility section gives the probe three outcomes and makes the third "any other error,
**or does not respond within a reasonable timeout**: the server is legacy". The deferral stands:
that sentence is descriptive rather than a tagged requirement, it sits inside a SHOULD-probe
recommendation, and the empirical pass above was run against this same revision. What it settles is
the shape of the eventual fix — a probe-scoped deadline that falls back, not the connect deadline,
which today swallows a silent server for `DefaultConnectTimeout` (120s) and then reports a bare
timeout rather than trying `initialize` at all. The HTTP binding says nothing equivalent; there the
fallback is keyed to an answered 400.

### 7.7 Ecosystem validation is stub-only, and the stub is HTTP-only

Conformance rests on `test/mcpstub` (§4.1), which is strict but is a stub, and on nothing else —
§4.2 and §4.3 were never wired. When the first real 2026 server ships, run against it before
trusting the interop further than the stub proves it.

**It is an `httptest.Server`, so everything it proves, it proves about streamable HTTP.** The stdio
2026 path is covered differently and less: `internal/testutil/fakemcp`, which every stdio test uses,
answers `initialize` and does not implement `server/discover`, so a `Handshake` against it always
falls back and every stdio test in the tree runs the pre-2026 path. What stands in for the stub
there is the pipe-based transport tests, which drive the same `transport.conn` that `SpawnStdio`
wires a child process into:

| stdio 2026 | Evidence |
|---|---|
| discover → 2026 negotiation, and no `notifications/initialized` after it | `TestHandshakeDiscover2026` |
| the three-outcome backward-compatibility rule | `TestHandshakeFallbackToInitialize`, `TestHandshakeKeepsModernServerOnSpecError`, `TestHandshakeDiscoverNoMutualVersion` |
| per-request `_meta` injection | `TestHandshakeDiscover2026`, on one request shape (`tools/list`) |
| `notifications/cancelled` forwarding | `TestCancelForwardsCancelledNotification` — but pre-handshake, so unnegotiated |
| **MRTR over stdio, in any form** | none |
| **`downstream.Connect` reaching 2026 over stdio** | none |
| **adversarial strictness** (missing `_meta`, wrong retry id or arguments) | none — that is `strictness_test.go`, and it is HTTP |

The missing rows are breadth rather than distinct logic, which is why this is recorded rather than
built: `CallFor` and the MRTR loop sit ABOVE the transport and are identical on both, so a stdio
MRTR test would mostly re-prove shared code over a different pipe. Closing it properly means
splitting the stub into a transport-agnostic core plus an HTTP front end that checks headers and a
stdio one that has none to check — worth doing when a real 2026 stdio server exists to compare
against, and not before, since the stub would otherwise be grading itself twice.

### 7.8 Subscription correlation data is received and unused

The listen stream opts into the three list-changed event types and dispatches by notification
method name, exactly as the legacy GET stream did. The per-event
`io.modelcontextprotocol/subscriptionId` is not read and `resourceSubscriptions` is not requested;
both become necessary only with per-resource subscriptions, which arrive with resource proxying
(§7.3). The acknowledgment notification *is* read — it is the only signal that a type asked for will
never arrive — but only to log the shortfall.

### 7.9 The exposure side answers `tools/list` in one page

The read side walks a downstream's pages (`listAllTools`), but the gateway's own answer is the whole
aggregated catalog in a single result and it ignores an incoming `cursor`. Page size is the server's
to choose, so one page is conformant; what is missing is the escape hatch for a catalog large enough
that a client would rather have it in pieces. Nothing here has met one yet, and the surface that
would need paging — the projection through the session's scope — is computed whole anyway.

### 7.10 `x-mcp-header` is neither mirrored nor validated

The specification lets a tool annotate an input-schema property with `x-mcp-header`, obliging a
client to mirror that argument into `Mcp-Param-{Name}` and a server to validate it against the body.
Neither face implements it: nothing here emits an `Mcp-Param-*` header, and nothing checks one.

The awkward part is the middle. `discovery.schemaOf` forwards a downstream's `inputSchema` verbatim,
so an annotation a downstream wrote is re-advertised to AgentHub's own callers — inviting a
conforming caller to mirror a header this gateway never checks, while AgentHub's outbound leg to
that same downstream never mirrors it either. Fixing one side alone makes the mismatch worse, which
is why both wait together.

### 7.11 Results other than discover carry no `serverInfo`

Servers SHOULD echo `io.modelcontextprotocol/serverInfo` in every result's `_meta`;
`gateway.replyResult` echoes it in none. `server/discover` and `initialize` both carry the identity,
so a client that wants it has it from the handshake — the per-result echo exists for intermediaries
reading one response in isolation, which is not how anything reaches this gateway today.

### 7.12 A 2026 stdio downstream is never subscribed

`subscriptions/listen` is transport-independent in 2026-07-28, and a conformant server sends no
notification a client did not subscribe to. `setNegotiated` opens the listen stream on the
streamable-HTTP transport only; the stdio `conn` records the request `_meta` and stops there. A
stdio downstream negotiated to 2026-07-28 therefore never announces a tools-list change, where the
same server on the older generation would have pushed it inline. Latent until a real 2026 stdio
server exists; the seam is `conn.setNegotiated`, matching the HTTP one line for line.

### 7.13 Trace context does not survive the hub

`traceparent` / `tracestate` / `baggage` are reserved `_meta` keys, and propagating them is
available rather than required — nothing here reads or writes any of the three. An upstream
client's `_meta` never reaches a downstream in any case: `CallToolParams` has no `_meta` member, so
the gateway rebuilds the params and `injectMeta` supplies agenthub's own. A trace therefore stops at
this hop and a second one starts, which is the honest description of what a proxy that mints its own
requests does — but it means an operator correlating a client's span with a downstream's cannot,
and that is worth knowing before reaching for the trace.

### 7.14 A truncated result has no `structuredContent`, and its tool's `outputSchema` said it would

`server/tools.mdx` is unambiguous where a tool declares an output schema: "Servers **MUST** provide
structured results that conform to this schema." AgentHub forwards a downstream's `outputSchema`
verbatim, so to its own client AgentHub is the server that declared it — and when
`internal/shaping` truncates, `paginate` returns `keepStructured = false` on every path where a cut
actually happens, so the delivered result carries no `structuredContent` at all.

**Nothing is destroyed.** The structured payload is the last segment of the linearized remainder, so
it is deferred whole and comes back through `fetch_result` — as text, in the paged continuation.
That is the documented rule ("a structured block is never split: it is deferred whole") and
`TestShapeGolden` pins it. The defect is not data loss; it is that page 1 is a `tools/call` result
which does not satisfy the schema its own `tools/list` advertised, and the trailer says only that
*characters* were truncated — a client cannot tell the structured channel was deferred rather than
absent.

Two fixes exist and both cost something this file will not spend unilaterally:

- **Never defer it.** Keep `structuredContent` on every page and let the never-larger guarantee
  decide whether shaping happens at all. It needs no new plumbing and matches the package's own
  stance that spending tokens beats withholding a caller's data — but it changes what the operator's
  byte budget means, because a result can then exceed it by the whole structured payload. That is a
  product decision about `budgetFor`, not a conformance cleanup.
- **Defer it only when no schema was promised.** Precise, and it needs `outputSchema` threaded from
  `router.Def` through `pipeline.CallRequest` — which today carries `InputSchema` and nothing else —
  down to `shaping.Options`. More code, and the distinction is thin: a downstream that sends
  structured content without declaring a schema still has clients that parse it.

Worth noting which way the encouraged shape falls. The specification tells a tool returning
structured content to **also** return the serialized JSON in a text block, so the common result is
roughly the same payload twice; keeping the structured half whole and paging the text half still
saves about half the bytes. The budget only becomes advisory for the uncommon result whose bulk is
structured and whose text is not.
