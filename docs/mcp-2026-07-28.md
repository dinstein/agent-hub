# MCP 2026-07-28 Support

This document captures the research, design decisions, and implementation plan for
supporting the MCP 2026-07-28 specification in AgentHub. It is the primary reference
for the `mcp-2026-07-28` branch.

Upstream specification: <https://modelcontextprotocol.io/specification/2026-07-28>  
Changelog from 2025-11-25: <https://modelcontextprotocol.io/specification/2026-07-28/changelog>

---

## 1. What changed — and what it means for this codebase

### 1.1 Breaking changes (require code changes before connecting to a 2026-07-28 server)

#### Stateless protocol — no more `initialize` handshake

The `initialize` / `notifications/initialized` round-trip is gone. Instead, every
outgoing request carries three `_meta` keys:

| Key | Required | Value |
|-----|----------|-------|
| `io.modelcontextprotocol/protocolVersion` | Yes | `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | Yes | `ClientCapabilities` object |
| `io.modelcontextprotocol/clientInfo` | SHOULD | `Implementation` object |

Servers SHOULD echo `io.modelcontextprotocol/serverInfo` in every result's `_meta`.
A request missing a required field is rejected with `-32602` (Invalid params) and HTTP
400 on HTTP transports.

**Backward compat rule**: when `NegotiateVersion` decides the server speaks 2025-11-25
or earlier, the old Initialize path stays in effect. The version is determined by
`server/discover` (see §1.1 below); if that RPC is absent (stdio probe), the transport
falls back to `initialize`.

#### `server/discover` — new required RPC

Servers **MUST** implement this RPC. It returns supported protocol versions, capabilities,
and server identity. Clients **MAY** call it before any other request to pick the highest
mutually supported version. On stdio it also serves as a backward-compatibility probe: if
the server does not answer `server/discover`, the caller falls back to `initialize`.

```json
// request
{ "jsonrpc": "2.0", "id": 1, "method": "server/discover", "params": {} }

// response
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "resultType": "complete",
    "protocolVersions": ["2026-07-28", "2025-11-25"],
    "capabilities": { ... },
    "serverInfo": { "name": "my-server", "version": "1.0.0" }
  }
}
```

#### `resultType` required on all results

Every result object must carry `resultType`:

- `"complete"` — normal successful result
- `"input_required"` — the server needs more information (see MRTR below)

For backward compatibility with 2025-11-25 servers, an absent `resultType` is treated
as `"complete"`.

#### Multi Round-Trip Requests (MRTR) — replaces server-initiated RPCs

The previous pattern of server-initiated requests (`roots/list`, `sampling/createMessage`,
`elicitation/create`) is **removed**. Servers that need client input respond with
`InputRequiredResult` on `tools/call`, `prompts/get`, or `resources/read`:

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "key1": { "method": "elicitation/create", "params": { ... } }
    },
    "requestState": "<opaque AEAD-protected blob>"
  }
}
```

The client must:
1. Collect the requested inputs.
2. Retry the **original** request with a **new** JSON-RPC id, carrying `inputResponses`
   and the echoed `requestState`.

Clients MUST NOT inspect or modify `requestState`. Servers MUST treat it as
attacker-controlled input and protect its integrity if it affects authorization.

#### Streamable HTTP: session ID removed, resumability removed

- `Mcp-Session-Id` header is gone entirely — no session capture, no DELETE on close.
- `Last-Event-ID` and SSE event IDs are gone — a broken response stream is a lost
  request; the client **must** re-issue it with a new request ID.
- The HTTP GET endpoint for out-of-band notifications is replaced by `subscriptions/listen`.

#### `subscriptions/listen` — new subscription stream

A single long-lived POST-response SSE stream replaces both the GET notification stream
and `resources/subscribe`/`resources/unsubscribe`. Clients opt in to event types:
`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`.
Each notification on the stream carries `io.modelcontextprotocol/subscriptionId` in
`_meta` for correlation.

#### Removed methods

| Removed | Replacement |
|---------|-------------|
| `ping` | (none; omit) |
| `logging/setLevel` | `io.modelcontextprotocol/logLevel` in request `_meta` |
| `notifications/roots/list_changed` | (deprecated — use MRTR) |
| `resources/subscribe`, `resources/unsubscribe` | `subscriptions/listen` |
| HTTP GET notification stream | `subscriptions/listen` |

#### Error code renumbering

| Code | Name | Old code |
|------|------|----------|
| `-32020` | `HeaderMismatch` | `-32001` |
| `-32021` | `MissingRequiredClientCapability` | `-32003` |
| `-32022` | `UnsupportedProtocolVersion` | `-32004` |
| `-32602` | resource not found (JSON-RPC Invalid Params) | `-32002` |

The range `-32000` to `-32019` is now "legacy" (grandfathered SDK usage, no new
allocations). `-32020` to `-32099` is reserved for the MCP specification.

#### Required Streamable HTTP headers

Every POST must now carry:
- `Mcp-Method`: the JSON-RPC method name
- `Mcp-Name`: the tool / resource / prompt name (when applicable)

### 1.2 New minor additions

- **`CacheableResult`**: `tools/list`, `resources/list`, `prompts/list`,
  `resources/read`, `resources/templates/list` results must carry `ttlMs` (freshness
  hint in ms) and `cacheScope` (`"public"` or `"private"`).
- **`extensions` field** in `ClientCapabilities` / `ServerCapabilities` for opt-in
  extensions beyond the core protocol.
- **Tasks** promoted from experimental to official extension
  `io.modelcontextprotocol/tasks`; redesigned with polling (`tasks/get`) and
  client-to-server input (`tasks/update`).
- **`tools/list` deterministic ordering** recommended for LLM prompt cache hit rates.
- **OpenTelemetry**: `traceparent`, `tracestate`, `baggage` in `_meta` per W3C Trace
  Context spec.
- **OAuth `iss` validation** (RFC 9207): auth responses SHOULD carry `iss`; clients
  MUST validate it against the recorded issuer before redeeming the code.
- **`application_type`** required in DCR requests.
- **Client ID Metadata Documents** as the preferred DCR replacement.

### 1.3 Deprecations (≥ 12-month window, minimum removal 2027-07-28)

| Feature | Migration |
|---------|-----------|
| `roots` feature | Pass directories via tool params, resource URIs, or server config |
| `sampling` feature | Integrate directly with LLM provider APIs |
| `logging` feature | Write to `stderr` (stdio) or use OpenTelemetry |
| HTTP+SSE transport | Already marked `DEPRECATED-UPSTREAM` in our code; migrate to Streamable HTTP |
| OAuth DCR (RFC 7591) | Use Client ID Metadata Documents |

## 2. Implementation plan

Work is split into three phases ordered by dependency. Each phase produces one or more
commits that each compile and pass `make ci`.

### Phase 1 — Transport layer (target: 2 weeks)

Goal: AgentHub can connect to a 2026-07-28 downstream server (as MCP client) while
remaining fully backward-compatible with 2025-11-25 and earlier servers.

**`internal/mcp/version.go`**
- Add `"2026-07-28"` to `SupportedVersions`.
- Keep `ProtocolVersion = "2025-11-25"` until Phase 1 is complete; flip it to
  `"2026-07-28"` as the final commit of Phase 1.

**`internal/mcp/types.go`**
- Add method / notification name constants:
  - `MethodDiscover = "server/discover"`
  - `MethodSubscriptionsListen = "subscriptions/listen"`
- Mark `MethodPing`, `NotificationInitialized` deprecated (comment, not delete — the
  old code path still handles 2025-11-25 servers).
- Add types:
  - `RequestMeta` — per-request `_meta` fields
  - `DiscoverParams` / `DiscoverResult`
  - `InputRequiredResult`, `InputRequest`, `InputResponse`, `InputRequests`,
    `InputResponses`
  - `CacheableResult` — embedded in `ListToolsResult` and sibling list results
- Add `ResultType string` to every result struct; add constants `ResultTypeComplete`,
  `ResultTypeInputRequired`.
- Add `Extensions map[string]json.RawMessage` to `ClientCapabilities`.
- Update error code constants: `CodeHeaderMismatch = -32020`, etc.

**`internal/mcp/transport/initialize.go`**
- Rename current `Initialize` to `initializeLegacy` (unexported).
- New exported `Discover(ctx, t, clientInfo) (*DiscoverResult, error)` — calls
  `server/discover` with the declared protocol version in `_meta`.
- New exported `Handshake(ctx, t, clientInfo) (negotiatedVersion string, serverCaps json.RawMessage, err error)`:
  1. Try `Discover`; if the server answers, select the highest mutually supported version.
  2. If the server returns method-not-found, fall back to `initializeLegacy`.
  - On 2026-07-28: returns early (no `notifications/initialized` notification needed).
  - On ≤ 2025-11-25: sends `notifications/initialized` as before.
- New `BuildRequestMeta(version string, caps ClientCapabilities, info Implementation) map[string]any`
  — produces the `_meta` map injected into every outgoing request when
  `negotiatedVersion == "2026-07-28"`.

**`internal/mcp/transport/streamablehttp.go`**
- Remove `sessionID`, `captureSession`, `deleteSession`, `ErrSessionExpired`.
- Remove `disableResume`, `lastEventID`, `resumeStream`, SSE event ID fields and logic.
- Add `negotiatedVersion string` field; set from `Handshake`.
- In `Call`: if `negotiatedVersion == "2026-07-28"`, inject `_meta` into `params`;
  add `Mcp-Method` and `Mcp-Name` headers.
- Replace `startNotificationStream` / `notificationLoop` / `openNotificationStream`
  with `startSubscriptionsListen` (long-lived POST stream requesting
  `toolsListChanged`, `promptsListChanged`).

**`internal/mcp/transport/httpcommon.go`**
- Add `headerMcpMethod = "Mcp-Method"`, `headerMcpName = "Mcp-Name"`.
- Remove `headerSessionID`, `headerLastEventID`.
- Add `HTTPConfig.SubscriptionsListen bool` flag (analogous to old `NotificationStream`).

**`internal/mcp/transport/stdio.go`**
- In `Call` for 2026-07-28 mode: inject `_meta` into outgoing request params.
- `Handshake` selects the path; the stdio transport stores `negotiatedVersion`.

**Tests**
- `transport/initialize_test.go`: add cases for `Discover` happy path, method-not-found
  fallback, and version mismatch returning `ErrUnsupportedVersion`.
- `transport/streamablehttp_test.go`: update wire golden files to remove session headers
  and Last-Event-ID; add `Mcp-Method`/`Mcp-Name` assertions.
- Update `internal/downstream` call sites that use `Initialize` directly.

### Phase 2 — MRTR (target: 2 weeks)

Goal: calls to a 2026-07-28 downstream server that returns `InputRequiredResult` are
handled correctly rather than being passed through as errors.

**Design: MRTR coordinator in `internal/downstream`**

`InputRequiredResult` is a connection-level retry concern, not a pipeline concern —
`internal/pipeline` should always see a complete result. The coordinator lives in
`internal/downstream` (or a new `internal/mrtr` leaf package) and wraps the raw
`Transport.Call`:

```
downstream.Call(ctx, method, params)
  → transport.Call → InputRequiredResult?
       yes → mrtr.Resolve(ctx, inputRequests) → inputResponses
           → transport.Call(ctx, method, params + inputResponses + requestState)
           → repeat until complete or error / max-retries
       no  → return result to pipeline
```

`mrtr.Resolve` dispatches each `InputRequest` by method:

| Method | Handler |
|--------|---------|
| `roots/list` | Returns the gateway's configured roots for this session |
| `elicitation/create` | Forwards to HITL approval broker (existing `internal/approval`) |
| `sampling/createMessage` | Returns `MissingRequiredClientCapabilityError`; AgentHub does not proxy LLM calls |

**Security**: `requestState` is opaque and echoed verbatim. The MRTR coordinator MUST
NOT inspect its contents. Servers own integrity; the client's only obligation is faithful
echo.

**`internal/pipeline`**
- `CallResult` already passes through verbatim. Ensure `defend_and_shape` runs on the
  final complete result, not on intermediate `InputRequiredResult` bodies.
- Add a counter assertion: an MRTR round-trip must advance the same gate counters as a
  direct call (no double-counting).

**`internal/mcp/types.go`** (Phase 2 additions)
- `CallToolParams` gains `RequestState string` and `InputResponses InputResponses` for
  the retry path.

**Tests**
- Add an e2e test that uses a local stub server (see §4) returning one round of
  `InputRequiredResult` with an `elicitation/create` request, verifying the HITL
  flow is invoked and the retry carries the correct `requestState`.

### Phase 3 — Subscriptions and OAuth (target: 1 week)

Goal: `subscriptions/listen` replaces the GET notification stream; OAuth aligns with
2026-07-28 auth spec additions.

**`subscriptions/listen`**
- The transport posts a `subscriptions/listen` request with desired event types.
- The long-lived response stream is an SSE feed; each event carries
  `io.modelcontextprotocol/subscriptionId` in `_meta`.
- Dispatcher maps `subscriptionId` → `ChangeMask` and calls `onChange` as before.

**OAuth**
- `internal/oauthflow`: add `Client ID Metadata Documents` support as the preferred
  registration path; keep DCR as the fallback for servers that do not support it.
- Validate `iss` in auth responses (RFC 9207) before redeeming the authorization code.
- Add `application_type` to DCR requests.

## 3. Backward compatibility strategy

| Scenario | Behavior |
|----------|----------|
| Downstream server speaks 2026-07-28 | `Handshake` → `Discover`, stateless `_meta` path, no `initialize` |
| Downstream server speaks 2025-11-25 | `Handshake` → method-not-found → `initializeLegacy`, old session/resume path |
| Downstream server speaks 2025-03-26 | Same as 2025-11-25 fallback |
| Upstream client speaks any version | Gateway's exposure side (the server face) is not changed in this branch — it always advertises what `internal/gateway` builds, which is version-agnostic from the client's perspective |

The `negotiatedVersion` field on each Transport instance gates every version-specific
code path. The gate is the transport's responsibility; nothing above `internal/downstream`
needs to know which protocol version is in use.

## 4. Test server strategy

No production MCP server has shipped 2026-07-28 support yet (as of 2026-07-30). The
following approaches are used in this branch:

### 4.1 In-process Go stub (primary)

A minimal `net/http` server in `test/mcpstub/` that implements exactly the new protocol
surface needed for the test suite:

- `server/discover` returning `["2026-07-28"]`
- `tools/list` with `resultType: "complete"` and `CacheableResult` fields
- `tools/call` with a happy path and one round of `InputRequiredResult` (elicitation)
- `subscriptions/listen` SSE stream emitting a `toolsListChanged` event

This stub has zero external dependencies and is built as part of `go test ./...`.

### 4.2 Go SDK beta

```bash
go get github.com/modelcontextprotocol/go-sdk@v1.7.0-pre.1
```

Used in integration tests tagged `//go:build integration` to validate against the
reference implementation. Not part of `make ci` (no network in CI); run with
`make e2e-integration` locally.

### 4.3 Python SDK beta (optional)

```bash
pip install "mcp==2.0.0b1"
```

A small Python script in `test/pyserver/` runs as a subprocess in the Docker-based e2e
suite. Useful for cross-language validation. Gated behind `TEST_PYSERVER=1`.

Phase 3 deviation, decided during implementation: **Client ID Metadata Documents stay a
seam** (`NewClientIDMetadataRegistrar`, returns `ErrNotImplemented`). Implementing CIMD
requires publishing a client metadata document at a stable https URL, and agenthub — a
local process — has no hosting story for one. DCR (now with `application_type`) remains
the registration path through the deprecation window (earliest removal 2027-07-28); the
registrar seam makes the eventual migration a constructor swap.

Phase 2 deviation, decided during implementation: `elicitation/create` input requests
are **not** forwarded to the HITL approval broker. The legacy reverse-RPC path answers
elicitation with method-not-found (the gateway's peer handler serves only `roots/list`),
and MRTR resolves inputs through that same peer-handler seam — so both protocol
generations behave identically. Wiring elicitation to `internal/approval` would be new
capability, not 2026-07-28 parity; it stays out of this branch and the seam
(`mrtr.Handler`) is where it plugs in later.

Deviation from the Phase 1 sketch above, decided during implementation: session
and resume handling in `streamablehttp.go` is **kept**, not removed — §3 requires
the ≤ 2025-11-25 fallback path to keep working, and that path still uses
`Mcp-Session-Id` / `Last-Event-ID`. The 2026 path simply never receives a session
id (the header is gone server-side). Removal happens when the deprecation window
closes, not in this branch.

## 6. Open questions / decisions deferred

1. **Should `ProtocolVersion` flip to `"2026-07-28"` when connecting to a 2026-07-28
   server, or stay at `"2025-11-25"` until we are fully conformant?**
   ~~Decision: flip only in the `_meta` of outgoing requests (transport-level), not as the
   global `mcp.ProtocolVersion` constant, until Phase 1 is complete and the test suite
   green. Then flip the constant as the final Phase 1 commit.~~
   **RESOLVED (Phase 1 landing): the constant never flips.** Every reader of
   `mcp.ProtocolVersion` is definitionally pre-2026 — the legacy initialize declaration
   (which only runs after `server/discover` failed), the exposure side's default answer
   (out of scope for this branch per §3), the pre-negotiation HTTP header, and fakemcp's
   scripted default. The 2026-07-28 declaration is carried per-request in `_meta`, built
   by `transport.BuildRequestMeta` from `Version2026` directly, so a global flip would
   change only the places where 2025-11-25 is the correct value. The constant's doc
   comment in `internal/mcp/version.go` records this.

2. **MRTR `sampling/createMessage` handling**: AgentHub does not route LLM calls today.
   Decision: return `MissingRequiredClientCapabilityError (-32021)` and do not declare
   `sampling` in the capabilities advertised to downstream servers (i.e., the
   `clientCapabilities` in `_meta` omits `sampling`).

3. **`tasks` extension**: not implemented in this branch. AgentHub's discovery already
   has a `fetch_result` meta-tool for paginated results, which covers the primary use
   case. Revisit in a follow-up branch once the extension spec stabilizes post-GA.

4. **`CacheableResult` on the exposure side** (AgentHub acting as MCP server toward
   upstream clients): not implemented in Phase 1. The downstream `tools/list` response
   cache already exists (`cache/tools/*.json`); surfacing `ttlMs` upward is a Phase 3
   or later addition.

## 7. Known gaps and the follow-up plan

Everything below is deliberate scope, not oversight: each entry names the gap, the
current (fail-closed) behavior, where the seam is, and what implementing it would take.
This section is the roadmap for the work that comes after this branch lands.

### 7.1 Exposure side still speaks only the stateful protocol

The gateway's server face answers `server/discover` with method-not-found
(`internal/gateway/upstream.go`, the dispatch default) and negotiates versions by
echoing the client's `initialize` declaration. A 2026-only client that cannot fall back
to `initialize` cannot connect. Implementing stateless exposure means: `server/discover`
in the gateway dispatch, per-request `_meta` parsing (version + capabilities), sessionless
operation in `internal/httpbridge` (today `initialize` is what mints the session), and
`Mcp-Method`/`Mcp-Name` validation with `-32020`. This is the largest single follow-up
and should be its own branch.

Related quirk, small and worth fixing first: `handleInitialize` echoes any version in
`mcp.SupportedVersions` — including `"2026-07-28"`, which the exposure side does not
actually implement. A client declaring 2026-07-28 inside a legacy `initialize` would be
promised stateless semantics that do not exist. The echo should clamp to
`mcp.Version2025` until stateless exposure lands (one line in
`internal/gateway/upstream.go` plus a test).

### 7.2 Extensions are not forwarded — fail closed by design

The `clientCapabilities` AgentHub declares downstream (`clientCapabilities2026`,
`internal/mcp/transport/initialize.go`) are empty: no extensions, no sampling, nothing.
A conforming server therefore never activates an extension (UI/MCPApp included) and
serves the non-extension fallback its spec obliges it to carry. The upstream client's own
capability declaration is deliberately NOT forwarded: the server's counterparty is
AgentHub, and AgentHub must only declare what it can itself deliver.

Supporting extension passthrough later means an allowlist policy, per extension, decided
one at a time: forward the upstream client's opt-in into the downstream `_meta` only for
extensions AgentHub can safely proxy end to end. A blanket forward is wrong in exactly
the way blanket capability declaration is wrong — the server would send payloads we
cannot honor.

### 7.3 Resources are not proxied, so `ui://` cannot flow

The gateway serves tools only (`initialize`/`ping`/`tools/list`/`tools/call`/shutdown).
MCPApp/UI content is delivered as `ui://` resources, which no client — old or new — can
fetch through AgentHub today. UI support is therefore three stacked pieces, in order:
resource proxying on the exposure side (through the same governance pipeline as tool
calls), the §7.2 extension-forwarding policy, and only then UI passthrough for clients
that opted in. Old-protocol clients keep the automatic degradation path: no opt-in
forwarded → server sends its text fallback (§7.2).

### 7.4 MRTR answers only what the legacy path answered

`elicitation/create` input requests fail with method-not-found — the same answer the
legacy reverse-RPC path gives, so the two generations stay in parity. Wiring elicitation
to the HITL approval broker (`internal/approval`) is new capability with its own UX
questions (what does a prompt rendered through an approval channel look like?); the seam
is `mrtr.Handler` in `internal/mrtr`, and `resolveInputs` in `internal/downstream/server.go` is where a
richer handler would be installed. `sampling/createMessage` stays refused (§6.2).

### 7.5 Result surface: 2026 fields leak upward, freshness hints do not

Two small asymmetries on the exposure side, both harmless under the spec's
unknown-member tolerance, both worth tidying when the exposure side is next touched:
a 2026 downstream's `resultType: "complete"` currently passes through to legacy
upstream clients verbatim (could be stripped at the gateway boundary), while
`CacheableResult` (`ttlMs`/`cacheScope`) from downstream `tools/list` is consumed
internally and never surfaced upward (§6.4 — becomes relevant once the exposure side
speaks 2026, where the fields are required).

### 7.6 Handshake probe hardening — evaluated, deferred with evidence

`discoverFallback` falls back to `initialize` only on proof the server answered (any
JSON-RPC error, or a ClassFatal HTTP 4xx). A server that crashes, hangs, or answers 5xx
on an unknown method fails to connect where it happened to work before. Two hardenings
were designed and deliberately deferred after an empirical pass (real stdio TS SDK
server plus two production streamable-HTTP servers, all falling back cleanly): widening
the fallback to any answered HTTP response, and a per-server `protocol: legacy` registry
escape hatch that skips the probe. Reach for the escape hatch first if a real server in
the wild trips this; it also serves as the operator's immediate mitigation.

### 7.7 Ecosystem validation is still stub-only

No production server speaks 2026-07-28 yet, so conformance rests on `test/mcpstub`
(strict by design) and the §4.2/§4.3 SDK betas remain unwired: the `go-sdk` pre-release
integration tests (`//go:build integration`, network, out of CI) and the Python
`TEST_PYSERVER=1` harness were planned but not built. When the first real 2026 server
ships, run the §4 matrix against it before trusting the interop further than the stub
proves it.

### 7.8 Subscriptions: correlation data is received and unused

The listen stream opts into the three list-changed event types and dispatches by
notification method name, exactly as the legacy GET stream did. The per-event
`io.modelcontextprotocol/subscriptionId` is not read, and the `resourceSubscriptions`
event type is not requested — both become necessary only with per-resource
subscriptions, which arrive with resource proxying (§7.3).
